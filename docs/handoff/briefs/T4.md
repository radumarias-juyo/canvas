# T4 · Scheduled runs: home conversation, scheduler, run executor, runs UI, Test it

Repo `radumarias/pi-artifacts`. Read first: `/mnt/project-files/agents-impl/plan.md` (architecture decisions 1-3),
`specs/routines-proposal.txt` (all of it; this task is its steps 1 and 2), and the "Runs" and "Delivery" sections of
`specs/tech-spec.md`. Base branch and PR target: **`feat/agents`**. This is the largest task: split it into two PRs
(engine first, then the UI and the workflow editor) if that keeps each reviewable.

## Goal

An agent with a trigger runs on its own: every day at a local time, or when a watched value changes, step by step, with
only `work` steps calling the model; each run is recorded and traceable; its report lands where people talk.

## Scope

1. **Home conversation**: turning on an agent (or its first run) makes its own chat (an ordinary `ChatAgent` of the
   owner, marked with the agent's id in the owner's `UserDirectory.chats` row), listed in the sidebar like a contact
   (badge, last post, unread) with the agent on its roster as the default speaker (a message with no mention there goes
   to the agent, not pi).
2. **Scheduler** (`Scheduler` from `agents/schedules`, installed in the chat object's `Lifecycle` with the harness and
   sockets): schedule triggers as one-shots at the next local time computed with `Intl` in the definition's `tz`
   (`days` respected), rescheduled after each run and whenever the definition changes or the agent is turned off
   (`UserDirectory` tells the home chat on save/enable/disable/delete). Watch triggers with `scheduler.every`.
3. **Runs**: `agent_runs` table in the home chat object (id, agent, due_at, item, status, session, started/ended,
   cost, summary, test flag), unique `(agent, due_at, item)` so a duplicate alarm sends once; one fresh pi session per
   scope item (`harness.sessions.create()`), a few at a time (cap 4); operation ids `run:<agentId>:<dueAt>:<item>`.
   Before a run: check the sign-ins of the servers it reads (T3's check; if T3 has not merged yet, detect the hub's
   "sign in required" error) → status `needs_sign_in`, no model call, kept to retry when `ChatAgent.signedIn(server)`
   is called (T3 calls it after a sign-in).
4. **Step executor** in code for the workflow (`AgentStep` in `shared/agents.ts`): `look` (an `McpHub.read` as the owner,
   result into the run session as a passive write, size-capped), `onlyIf` / `if` (a small, safe expression language
   over earlier results: numbers, strings, comparisons, `and`/`or`/`not`, arithmetic, percent change, paths into JSON
   results; parsed, never `eval`), `work` (submit the prompt into the session, with the named skill; the only model
   call), `tell` (to `chat` = the home conversation as a `chat.agent` post with the run id, to people = notification via
   the sidebar notice and T3's `UserDirectory.push`, `via {server, tool}` = an outside tool: refused at autonomy 1 until
   T6 adds the gate), `page` (artifact findings edit or snapshot through `artifact_write`/`artifact_check`/
   `artifact_publish`; a failed check records "page not updated" and the run still reports), `handOver` (a turn for
   another agent of the owner in the home chat), `do` (refused until T6). Scope `each`: list once with the scope's
   `look`, then run per item. A run with nothing to report ends `not_today` without a model call.
5. **Compile instructions to steps**: when a definition with a trigger is saved without a `workflow`, or the person asks,
   one model call (the agent's model or the chat default, low effort) turns the instructions and the at-a-glance fields
   into `AgentStep[]` validated by `checkAgent`; the person can edit the list (next item).
6. **Workflow tab** on the agent page (T2 builds the page and its `TABS`): the step list with kind labels When, Look at,
   Work out, Only if, If, Do, Tell, Page, Hand over; reorder by drag and by keyboard, edit, add, remove; Save writes the
   definition.
7. **Runs tab** and **run detail** per the mockup: list (when, why: schedule / watch / test, status, cost, duration),
   detail ("Acted on 5 of 7", "Not today" items, what it sent and to whom, how it got there = the trace from the run
   session's entries with the step rows the chat already draws, what it used: skills, memory, servers, cost).
8. **Test it** (`POST /api/agents/:id/test`, button on the draft card and the agent page): the same executor in a fork
   with `tell` and `do` replaced by recorders; shown as a run marked "test"; nothing sent or changed.
9. **Replies continue a run**: a reply to a run's post (in the home chat or a shared chat) gives the agent a turn in a
   `sessions.fork()` of that run's session, so it answers with the run's numbers in context.
10. **Posting into shared chats**: `tell` to a chat where the agent is on the roster and its owner is a member: RPC into
    that chat object, a `chat.agent` entry marked as scheduled with the run id.
11. **Watches shared by many people** go through a new `Source` Durable Object keyed by the hub's call identity: it
    polls once per interval, keeps a hash of the last result, and tells subscribers only when it moves. New class in
    `cloudflare.config.ts`.
12. A `DEV_TOOLS` route to fire a run now (local dev), like the dev publish route.

## Acceptance

The spec's tests: a duplicate alarm sends once; a local 07:00 survives a DST change; a false condition makes no model
call; a reply sees the run's numbers; a Source polls once for two subscribers; a page that fails its check isn't
published. Plus expression-language tests and executor tests with fakes. Suite green, typecheck clean. Screenshots of
the home conversation in the sidebar, a run post, the runs list and detail, the workflow tab, a test run, in
`docs/media/scheduled-agents/`. `/complete-review-and-fix` before each PR.
