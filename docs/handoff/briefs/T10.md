## Scope

1. **Router**: when a chat allows it (a chat setting, off by default; on by default only in private chats with agents)
   and nobody is named, a small Workers AI model (like the call hint in `worker/agent/call-hint.ts`, Jev or the router
   used by Auto) picks zero to two agents from their names and job lines. Logged (metrics), a failure picks none.
2. **Unprompted posts** behind a funnel: gates (the agent allows it, the chat allows it, not muted, budget left), a pause
   in the conversation, an interest match (embeddings on Workers AI between the recent messages and the agent's job),
   then the agent gets a turn and may answer `PASS` (nothing posted). Posts are marked "unprompted" with a per-chat
   **mute** for that agent. **Follow-ups**: through the same funnel, an agent may offer to pick up a request left
   unanswered ("Radu asked yesterday for the campaign list and nobody has answered. Want me to pull it?").
3. **One offered next step**: an answer may end with one offer, such as "Send this to Maria every Monday?"; saying yes
   opens a routine draft (`agent_propose` with a schedule).
4. **The agent knows the app**: a built-in skill (`worker/skills/builtin/`) with the app's own help (chat kinds,
   branches, follows, agents, runs, limits) so anyone can ask "what can we do in this chat?".
5. **Big asks in stages**: an agent posts a plan as a checklist message and updates it live as each stage finishes (a
   tool for it, rendered as a checklist card that edits in place).
6. **Limits per chat**: the chat's owner sets which servers agents may use in that chat and a daily token budget for the
   chat (turns stop at the cap with a notice).
7. **Spend**: AI Gateway metadata on every model request tags uid, agent and run (the gateway's custom metadata header);
   a daily meter per user in `UserDirectory` stops scheduled runs at a cap (config, notice to the owner).
8. **Cache shares and metrics**: the hub's 16 MB read cache gets a budget per agent (even split with a floor; eviction
   starts with whoever is over its share); an optional Analytics Engine binding `METRICS` (no-op when absent) records
   cache hits/evictions per agent, memory and CPU per turn, run outcomes, router picks. Large tool results go to an R2
   file in the owner's folder with a short summary in context (through `worker/storage/`).

9. **What is there now** (merged into feat/agents at cd654c9): T1's group chat UI (people bar, @ picker, live agent
   turns, item chips), T2's editor and draft card (`agent_propose` already takes a schedule; T4 added watches with a
   condition language, `shared/conditions.ts`), T4's runs (home conversation per agent, `RunStatus`, Test it), T5's chat
   kinds (`answersEveryMessage` in `shared/chat-kinds.ts` is where a router default for private chats with agents fits),
   T3's Web Push. Turn tools are `allowedTools` in `worker/agents/turns.ts`; an unprompted post is a turn nobody asked
   for, so it gets only read tools of the shared servers. T7 (#111, memory notes) and T8 (#110, members' agents) are
   in review: merge feat/agents often.
