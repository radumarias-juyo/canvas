# T1 · Group chat UI and rules for agents

Repo `radumarias/pi-artifacts`. Read first: `/mnt/project-files/agents-impl/plan.md` (rules, phase 1, architecture),
then `specs/multi-agent-proposal.txt` sections 1, 2, 5, 6 and 8 ("Small touches"), and `specs/tech-spec.md`.
Base branch and PR target: **`feat/agents`** (never `main`).

## Goal

Make several agents in one chat feel like the proposal's mockup "a chat with three agents, mid hand-off": people and
agents side by side, each agent's work visible while it runs, and its own Stop.

## Scope

1. **Agent sessions stream to the chat.** Today only pi's root conversation streams over the chat socket
   (`ChatSockets`, `useChat`). Stream each roster agent's session too while it has a turn, with the events carrying the
   agent's id, so the app can show that agent's live steps (the same step rows pi has, `StepRun`), its elapsed time, and
   a **Stop** for that agent only (`abort` with `agent`, already in the protocol). Keep a socket's snapshot cost low:
   a socket that attaches mid-turn gets the running turn's entries, not the agent's whole history.
2. **People bar**: people first, then a divider, then pi and the agents (each with its own badge colour, `AgentBadge`),
   a working dot on the one that runs, an "off" look for one its owner turned off; hover says job line and owner.
3. **The `@` picker** (`src/chat` composer mentions) lists **Agents** (badge, name, job line, owner as a pill) above
   **People**. Picking an agent calls it; picking a person only tags them. Agents come from the chat's roster (the
   `agents` socket message and `GET /api/chats/:id/agents`).
4. **Queue line**: when a hand-off waits ("builder is next: research named it · hand-off 1 of 3"), show it as a dashed
   line under the running agent, as in the mockup; turns queued for an agent show their count.
5. **Adding and removing agents** (owner only): an "Agents" control in the people bar / header lists the owner's agents
   that are on, with Add; each agent in the bar has Remove in its menu. Members see the roster read-only.
6. **Who speaks**: in a chat with one person and no mention, pi answers (unchanged). In a shared chat agents answer only
   when called (`@name` or a reply to them; already in `#prompt`). Make sure a reply to an agent's message calls that
   agent (the `ReplyQuote` with `agentId`) and the reply UI quotes agent messages correctly.
7. **Every message shows its author's badge** (person, pi or agent), also in a chat without members once it has agents.
8. **Small touches from section 8**: long replies (pi's and agents') fold behind "Show more" past a height, so a busy
   chat stays readable; the working line shows the step's short phrase next to the timer ("pi · 6s · looking for this
   week's signups": use the assistant's text right before a tool call, or the tool's own title, cut short; never a new
   model call); **item chips** under a reply for records the reply is built on, taken from tool results the hub saw
   (server, id, title, link fields when a result has them), never from the model's text.
9. The `/api/chats/:id/agents` turn views: a small "Runs" popover per agent (its latest turns: who asked, when, how long,
   done/failed/stopped) from the people bar.

## Out of scope (other tasks)

Agent editor and drafts (T2), scheduled runs (T4), chat kinds and the add-by-tagging card (T5), members bringing their
own agents (T8), router and unprompted posts (T10).

## Acceptance

- Unit tests for any new pure logic (event routing per agent, fold rule, chips extraction, picker ordering), the existing
  suite green, `pnpm typecheck` clean.
- Run the app locally (`AUTH_MODE=demo PI_OFFLINE=1 PI_NO_DOCKER=1 pnpm dev`, see CLAUDE.md; without a model you can
  still render a chat with seeded entries or use the dev publish route) and take screenshots of a chat with agents:
  people bar, picker, a running agent with Stop and queue line, folded long reply. Light + dark, desktop + phone width,
  in `docs/media/group-chat-agents/`.
- `/complete-review-and-fix` on the change before the PR.
