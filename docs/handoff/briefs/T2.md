# T2 · Agent editor, the draft card, shared agents and copies

Repo `radumarias/pi-artifacts`. Read first: `/mnt/project-files/agents-impl/plan.md`, then
`specs/multi-agent-proposal.txt` section 4 (the agent editor mockup) and `specs/routines-proposal.txt` sections 1, 2,
3 and 7 (draft card, at a glance, Assumed, shared agents and "make it mine").
Base branch and PR target: **`feat/agents`**.

## Goal

People create, edit, turn on and share their agents, and see the model's proposals as draft cards in the chat.

## Scope

1. **Agents in the sidebar and an agent page.** An "Agents" section like Skills (collapsible, starts closed), listing the
   user's agents with badge, name, job line, on/off and "Draft" for proposals. Opening one shows the **agent page**:
   header (badge, name, job line, state pill "Proposed by pi · off" / "Draft · off" / "On", Turn on / Turn off), and
   tabs. Build the page so later tasks add tabs without touching each other: a `TABS` list in
   `src/agents/AgentPage.tsx`; this task ships the **Setup** tab; T4 adds Workflow and Runs, T6 Limits, T7 Knows.
2. **The Setup form, per the mockup**: name (`called as @name`), job line, instructions (Markdown textarea), avatar
   (up to 3 letters) and colour (`AGENT_COLORS`), model and effort (reuse the composer's model picker and effort
   control), and the **servers table** with two switch columns: "This agent" (`servers`) and "Shared chats"
   (`sharedServers`), each row with the server's name and whether it signs in each user ("signed in as you" / "no
   sign-in"). Servers that sign in as the user start off in the shared column; turning one on warns that the chat will
   see what the agent reads. Footer: "Saved in your user directory · version N · used in M chats" (M from a small index
   the chat objects keep in the owner's directory when they add or remove the agent: add it). Save uses the version it
   read (`PUT /api/agents/:id` with `version`); a conflict says someone changed it and reloads.
3. **Create**: "New agent" in the section, and from a chat "Make an agent" (the composer's + menu) which asks pi to
   draft one (it uses `agent_propose`).
4. **The draft card in the chat**: when `agent_propose` ran (its tool result's `details` are `AgentProposedDetails`), the
   chat shows a card instead of a plain step: header (badge, name, job, "Draft · off"), the instructions as numbered
   readable steps, and the **at a glance** rows Scope, Runs, Reads, Tells, Knows from the definition's fields, each with
   **Change** (opens the agent page at that field) and an **Assumed** badge for fields in `assumed`; buttons **Test it**
   (calls `POST /api/agents/:id/test`, which T4 implements; until then the button is hidden when the route answers 404)
   and **Turn on**. Turning on or saving clears `assumed` for the fields the person confirmed.
5. **Shared agents and copies**: the owner can share an agent with the people of a chat it is in (a switch on the agent
   page per chat, stored in the roster). Others in that chat can open it read-only (instructions, job, servers, latest
   turns) via a chat-scoped route; it keeps running as its owner. Their first change makes **their own draft copy** in
   their directory with `copiedFrom: {owner, id, version}` (the original is untouched), runs with their sign-ins, and
   says so.
6. **Delete** with a confirm that lists the chats it is in; those chats drop it (the roster already removes agents whose
   definition is gone at their next turn; also tell open chats now).
7. **Data export/import** (`shared/data-export.ts`, the account menu's export): include the user's agents; import never
   overwrites an existing one (same rule as skills).

## Out of scope

Running Test it, schedules, runs and workflow editing (T4); limits (T6); memory (T7).
