## Scope

1. **One write gate in the hub** (`worker/mcp/hub.ts` and its callers): every MCP call whose tool is not read-only goes
   through a policy check with the call's context (agent id and autonomy, who asked, run or chat turn, owner present?).
   Level 1 refuses; 2 returns a **proposal card** (the exact server, tool and input) the owner presses to run; 3 stores a
   **pending action** that waits for approval and expires (a `Scheduler` one-shot, default 12 hours, set per agent);
   4 runs it when the guardrails pass, and logs every call. A turn another agent started can't go above the level of
   the agent it handed over to; assistants in a chat (pi and roster agents on a person's turn) stay at level 2 unless
   the owner asked directly in their own view.
2. **Guardrails**: rules `{server, tool, arg, kind, value, effect}` with kind min | max | maxChange (versus the current
   value, read through a named read tool) | never | quietDates | callsPerDay and effect block | approve | warn; checked
   against the tool's input schema before the call leaves the object; the strictest rule wins. Stored with the agent
   (or per user for all agents).
3. **Approvals**: `pending_actions` with the exact call; the approver (the owner) sees Approve / Decline in a "Needs you"
   list (a section in the sidebar or account area, and a card in the chat where it came from); on Approve the object
   runs the stored call itself, exactly as stored; the run gets the result as an `app.approval` input and continues.
   Web Push (T3's `UserDirectory.push`) for approvals waiting.
4. **Limits tab** on the agent page (T2's `TABS`): the autonomy select (1 Inform, 2 Recommend, 3 Approve, 4 Run) and the
   rules list, with the rule editor **generated from the tool's input schema** (pick server, tool, argument; the kinds
   that fit the argument's type), the pending-actions expiry, quiet dates.
5. **Tell through outside tools** (`tell.via = {server, tool}`, e.g. a mail server's send tool) at level 4, or 3 with
   approval; recipients from the step.
6. Enable `do` steps in the run executor (T4 refused them) through the gate.
7. **pi on a hand-off**: an agent's reply naming `@pi` hands pi a full turn (a `chat.turn` input in the root session,
   `ChatTurnData.root` set), which runs with all of the owner's tools. T4 already closed the unattended case: a run's
   hand-over chain stores `unattended` on its turn rows, every hand-off copies it, and such a chain only tells pi
   (`tellPi`, a passive write), never gives it a turn. Left for this task: a chain a member started (or any root turn
   that was not the owner's own, `byOwner`) still gives pi a full turn. With the gate, that turn of pi's is not the
   owner's: its writes become proposals (level 2).

8. **What is there now** (merged into feat/agents at cd654c9): runs record a `do` step as "not done: writes wait for
   approvals" (`worker/agents/runs/executor.ts`, the `case "do"`), and a `tell` with `via: {server, tool}` is refused at
   Inform; the compile prompt already says a `do` waits for the owner's approval (`worker/agents/runs/compile.ts`).
   Run tools come from `runTools` / `#configureRun` in `worker/chat-agent.ts`; chat turns from `allowedTools` in
   `worker/agents/turns.ts`. Web Push is `UserDirectory.push(message)` (T3; it sends only when no app socket is open).
   `AgentDefinition.autonomy` (1-4) is stored and validated in `shared/agents.ts`. A page a run rebuilds must not call
   write tools it did not call before (T4 is fixing that; keep it when the gate lands). If T8 (#110, members' agents) is
   merged first: a member's agent runs as a seat in the member's own chat object, and `Caller.byOwner` holds only when
   the asker is that agent's owner; the gate must take the seat's owner as "the owner".
