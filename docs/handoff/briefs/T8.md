# T8 · Members bring their own agents, and uneven access

Repo `radumarias/pi-artifacts`. Starts after T1 merged into `feat/agents`. Read first:
`/mnt/project-files/agents-impl/plan.md` (decisions 5 and 6), sections 3, 4 and 6 of `specs/multi-agent-proposal.txt`
("Phase 2, a member's agent", "When members have different access", the review-before-posting mockups) and "Uneven
access" in `specs/tech-spec.md`. Base branch and PR target: **`feat/agents`**.

## Scope

1. **A member's agent in a shared chat**: a member adds one of their own agents (on) to a chat they are in. The roster
   row names the member as owner. The agent runs as a **seat**: a pi session for this chat inside the member's own agent
   home object (T4 makes one per agent; until then a chat object of the member for the agent), never in the owner's
   object, so the member's sign-ins, files, skills and budget stay theirs. The room (the owner's chat object) delivers
   log entries to the seat by RPC with a delivered seq (gap repair: a seat that misses a seq pulls the range), gives
   turns by RPC, and the seat posts its reply back by RPC. The chat sees only its name, avatar and job line. Names are
   unique per chat (a second planner shows as `@planner-ana`). Removing a person removes their agents; their past
   messages stay.
2. **Permissions**: the person who asks decides the tools. The agent's owner calling it: all of their servers. Anyone
   else: only the owner's shared-chat list, read-only (phase 1's `allowedTools` in `worker/agents/turns.ts` already encodes it as an allow-list the
   harness enforces; make the seat apply it). A per-person rate limit on each agent (a Rate Limiting binding like `PAGE_CALLS`, new binding `AGENT_TURNS`).
3. **Uneven access forks**: an owner's turn that may reach a server outside the agent's shared list runs in a
   `sessions.fork()` of the agent's chat session; only the posted reply returns to the shared session (as a write), so
   later questions from others can't pull private results out. The hub records which servers each turn called; a reply
   built on a private server carries a **source chip** ("from Ana's calendar · posted by Ana"). Optional **review before
   posting** (a per-agent setting): the reply shows first as a draft only its owner sees ("Only you can see this draft ·
   planner used calendar · private") with Post to chat / Edit / Discard.
4. Applies to the owner's own agents too (phase 1 runs their private turns in the shared session: move those to forks).

5. **Notes from the lead's reviews of T1 and T2** (merged): today an owner-asked turn streams its live steps to every
   socket in the chat (`#followAgents` / `TurnFilter` in `worker/chat-agent.ts`, `worker/agents/live.ts`), and its
   reply's item chips (`itemsIn`, `#outputs` in `worker/agents/controller.ts`) come from every server it called. With
   forks: a fork's turn must not be followed for other people's sockets (show them only that the agent is working, its
   phrase at most), and the reply posted from a fork carries item chips only from servers the agent shares with the
   chat, plus the source chip. Drafted agents already never share sign-in servers (`withoutSignInShares`). Turn ids
   continue past an imported log (`importedRoster`); keep operation ids (`turn:<id>`, `agent-reply:<agent>:<turn>`)
   unique in any session a seat or fork reuses.

## Acceptance

result never reaches the shared session; a duplicate delivery is placed once; a seat with a gap pulls the range.
