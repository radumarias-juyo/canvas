# T3 · Background MCP sign-in, and Web Push

Repo `radumarias/pi-artifacts`. Read first: `/mnt/project-files/agents-impl/plan.md`, then
`specs/mcp-background-signin.md` (the whole task list is there) and the delivery table in `specs/tech-spec.md`.
Base branch and PR target: **`feat/agents`**.

## Goal

Scheduled agents (T4) can use the owner's per-user MCP sign-ins with nobody present, safely, and people get told when a
sign-in is needed, when it is about to run out, and when something arrives while the app is closed.

## Scope

1. The seven app changes in `specs/mcp-background-signin.md`: encrypt `mcp_auth` records at rest with AES-GCM and a
   per-user key derived from a Worker secret (reuse the derivation pattern of `FILES_MASTER_KEY`; a new secret
   `MCP_TOKENS_KEY`, falling back to deriving from `FILES_MASTER_KEY` with a distinct label so existing deployments need
   no new secret; migrate plaintext rows on read); store the sign-in time and a configured grant length (config
   `MCP_GRANT_DAYS`, default 30); an API to **check the sign-ins a run needs** before it starts
   (`UserDirectory`/hub: connect non-interactively and refresh; answer per server `ok` | `needs_sign_in`); **notices**:
   `UserDirectory.notifySignInNeeded(server, context)` puts a sidebar notice and a browser notification with the
   sign-in link; after the sign-in callback (`worker/mcp-routes.ts`) call a hook that tells the chat objects with runs
   waiting on that server (expose `UserDirectory.onSignedIn(server)` that calls `ChatAgent.signedIn(server)` on the
   user's chats that registered interest; T4 implements what a chat does then); **warn ahead** a few days before the
   stored grant ends (an alarm in `UserDirectory`), once per grant; a daily keep-alive refresh for servers that runs use
   (in case idle sessions end after 24 h); **disconnect** a stored sign-in from the account menu (list servers with
   their sign-in time, Disconnect deletes the record).
2. **Web Push**: VAPID keys from secrets (`PUSH_VAPID_PUBLIC_KEY`, `PUSH_VAPID_PRIVATE_KEY`, `PUSH_SUBJECT`), RFC 8291
   aes128gcm payload encryption and RFC 8292 VAPID JWT with WebCrypto (no Node-only library), a `push_subs` table in
   `UserDirectory` (subscribe/unsubscribe routes, prune on 404/410), a service worker in the app that shows the
   notification and opens the right chat, and an opt-in in the existing notification ask card. One API for other tasks:
   `UserDirectory.push({ title, body, url, tag })` (body says only that something arrived, never data). Without the
   secrets everything still works (no push).
3. Keep scheduled runs read-only: provide a helper the run code (T4) uses to get only read-only tools of a server.

## Acceptance

Tests: encryption round trip and migration of plaintext rows, the check answers against the stand-in portal in
`test/mcp-oauth.test.ts` (signed in, refresh works, refresh refused → needs_sign_in), warning timing, push payload
encryption against RFC 8291's test vector, VAPID JWT shape. Suite green, typecheck clean. Screenshots of the account
menu's sign-ins list, the notices, in `docs/media/background-signin/`. Document the new secrets in the README's setup
section and in `deploy-guide` notes (`/mnt/project-files/deploy-guide/`) without any deployment's values.
