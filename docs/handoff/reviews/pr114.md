## Must fix

1. **Medium · `worker/chat-agent.ts` ~2985 `#spill`.** Every MCP result over MAX_TOOL_TEXT goes to the owner's general
   files as `tool-results/<chatId>/<tool>-<hash>.txt`, from any session: pi, a member's read-only turn, a run's work
   step. Names come from the content, so every new result adds a file, and nothing removes them but deleting the chat
   (a watch every 15 minutes adds about 96 a day).
   - The prompt's `user_files` index lists the newest files first, so after some 75-150 spills it shows only spill
     files in every chat, and the user's uploads drop out of what pi is shown. Each new spill also changes that
     prompt section in every chat (the cache). The folder summary gets one `tool-results/<chatId>` entry per chat.
   - `UserFiles.list()` stops at 2,000 keys in key order, and "out/" < "tool-results/" < "uploads/". Once those two
     hold 2,000 files, uploads vanish from GET /api/files, `findFiles` by name, `chatFiles()` and the @ list.
   - A member's read-only questions now write into the owner's storage.
   - Fix: keep spills out of the user's files. Store them under their own prefix through a small class in
     `worker/storage/` (read back by the path in the spill note; `files_read` can take it), or at least have
     `list()`/`filesIndex` and the sidebar skip `tool-results/`. Bound them: the newest N per chat, or delete those
     older than a day or two. Add a test that spills don't show in the index and are pruned.
2. **(split, my call) Medium · `shared/offers.ts` ~49 `offerOf`.** The offer line is cut to 200 characters, and the
   rest of it is shown nowhere (the bubble shows only the body). Yes sends "Yes, please set that up." as the owner's
   reply, which starts an owner turn with all of the owner's tools, and the agent acts on its whole previous line. A
   member's read-only turn can therefore end with an offer whose visible part is harmless and whose hidden part asks
   for a write. One checker said the model may not follow the hidden part; I don't want the owner's Yes to depend on
   that. Fix: never cut an offer. A last line over MAX_OFFER is not an offer and stays in the body. And make Yes do
   what the brief says: open a routine draft. Give the turn it starts the draft tool only (`agent_propose`, saved off),
   or at least label the reply so the agent only proposes. Add a test with a long last line.

### Must fix

11. **Low-medium, security · `shared/offers.ts` ~23 `offerYes`, item 2's gap.** Yes now copies the offer text into the
    owner's own message. A member can have a read-only turn end with an offer that carries invisible characters (Unicode
    tag characters U+E0020..E007E, which `offerOf`'s whitespace replace keeps and browsers draw as nothing). The owner sees
    only "Send this every Monday?", clicks Yes, and the hidden text arrives as the owner's words in a turn with all the
    agent's tools. A Markdown reference definition in the body (`[//]: # (…)`) is a second channel the owner never sees.
    Fix both ways:
    - Enforce the draft in code. Send a Yes as a flag (or the offer's entry id) with the prompt, and configure that turn
      with `agent_propose` plus read tools only, for a roster agent and for pi. The label can stay.
    - In `offerOf`, strip invisible and format characters (`/[\p{Cf}\p{Co}\p{Cn}\u{E0000}-\u{E007F}]/gu`, which covers
      zero-width and bidi controls too), or refuse such a line as an offer. In `offerYes`, refer to the offer by its reply
      quote, not as the owner's words.
    - Tests: a Yes turn's allow-list, and an offer with tag characters.

16. **Medium · `worker/chat-agent.ts` ~891 `#replying`.** It is `pi.inspect().submissions.length > 0`, and
    pi-durable's `inspect` counts the queued and placed submissions of every conversation, so roster turns, run steps
    and page rebuilds all count. (The harness's own `pending({session})` filters by conversationId.) Two failures:
    (a) pi is idle while @atlas works, and the owner's Yes is refused with "pi is still working". (b) A Yes is taken,
    and the owner then asks @atlas while pi drafts. At settle, `#piTools(false)` sees atlas's submission and returns.
    The root watch has ended, so nothing retries, and DRAFTING stays set. atlas then hands off to @pi, and
    `handToPi` never calls `#piTools`. pi runs the owner's attended request with draft tools only: no artifact
    tools, no files_write, no run_python. Any owner message to pi sent while an agent turn or run step is pending runs
    narrowed the same way. In a home conversation with a watch that's routine.
    Fix:
    - Count only the root conversation's submissions (filter `conversationId === ROOT_CONVERSATION_ID`).
    - Retry a skipped restore: `#place(() => #piTools(false))` in `handToPi` before it submits, and again when an
      agent turn ends while DRAFTING is set.
    - Tests for (a) and (b).
