## Must fix

1. **Medium, security · `worker/memory/chat.ts` ~125 `section` / pi-durable's prompt planner.** A private chat shows
   the owner's "just me" notes in the `memory` section. Those notes come from all of their chats. Sharing the chat (an
   invite, so `kindAfterJoin` makes it a group, or a kind change) reads the section again. But `planSystemEntries`
   only appends a patch: the first `pi.system` entry, with the old section, stays in the conversation. For models whose
   compat keeps mid-conversation system messages (`supportsMidConvoSystemMessages`; the two checkers disagree on whether
   the default gateway entries set it, and some entries in `worker/models.ts` set it for sure), the model still gets
   the owner's private notes on the member's turn. That breaks the brief's acceptance rule. Fix: when a conversation's
   audience widens and its shown section held `user` notes (SHOWN_KEY tells which), make the next generation write a
   fresh baseline that drops the earlier `pi.system` entries (a compaction or head marker, or context edits that
   omit them). Do it from `#joined` and `changeKind`, for pi's conversation and every agent session. Add a test that
   checks what the next model request after sharing carries, not ChatMemory's cache.
2. **Medium, security · `worker/memory/chat.ts` ~82 `#writer`.** pi's writer is `byOwner = reader.alone`. A pi turn
   that an agent's reply handed over (`handToPi`) therefore counts as the owner's own. An agent asked by nobody, or
   steered by MCP text, can reply "@pi remember …". Its note is then saved confirmed in "just me" and lands in every
   future private chat's prompt, and `memory_forget` is allowed too. Fix: tell ChatMemory who asked for pi's current
   turn. A handed-over pi turn (and any pi turn not started by the owner's own message) writes as not the owner: its
   notes wait for a confirm and forget is refused. Add a test. (After cd654c9, an unattended chain never gives pi a
   turn, but member-started chains still do.)
3. **Medium · `shared/memory.ts` ~133 `byRank`.** The prompt ranks notes by pinned, then uses, then newest, and the
   prompt itself adds the uses. Once the budget is full, the shown set feeds itself and stays fixed: a new
   preference ("report in EUR") is never shown, while the older one it replaces ("USD", uses 3) stays. Fix: rank
   pinned first, then by recency (updated or created). Keep uses only as a tie-break or for display. Add a test where
   a new note joins a full budget.

## Should fix

4. `worker/memory/store.ts` ~140: members and page joiners can fill the owner's account-wide unconfirmed cap (30)
   through pi ("@pi remember for this chat …"). After that, the owner's own agents can't save facts anywhere, and
   forgotten rows still count toward MAX_NOTES. Count non-owner saves per chat. A dismissed unconfirmed learned note
   should be deleted, not forgotten.
5. `worker/memory/memory.ts` ~133 `recall`: an empty query returns the top 20 by the prompt's own rank, which are
   the notes already in the prompt. The "N more notes are kept: memory_recall finds them" line points at notes it
   can't list. Return the notes not shown in this conversation first (ChatMemory knows the shown ids), or page
   through them, and don't promise "all of them" when the result is capped.
6. `worker/chat-agent.ts` ~512 `#install`: moving memory to the end on every new install means that when a later
   section key appears (skills' first pick with SKILLS_MODEL, user_files, mcp_servers), `planSections` removes and
   re-adds every section, the whole prompt included, instead of a one-key append. Only an extension that adds a new
   key needs to go last. A note's text change is already patched in place wherever the section sits. Use a plain
   `registry.install`, or move only an extension that brings new keys.
7. (split, low) `worker/memory/store.ts` ~135 `add`: saving the same text again as a preference confirms a waiting
   fact (`#same` ignores kind and confirmed). A learned save should not confirm a waiting fact. Only a person's add
   or edit should.

### Must fix

10. **Medium · `worker/agents/runs/store.ts` ~326 `agentOfSession`.** pi's root conversation is "1", and
    `instr(detail, '"1"')` matches any run row whose detail holds the string "1". That includes `sent: ["1"]` for a
    delivery at step key 1 ("look, then tell"), a rebuild session keyed "1", or a watch value. From then on, pi in that
    agent's home chat counts as the run agent: its section drops the owner's "just me" notes, its saves go to the

    Keep rebuild sessions in a column (or `json_each` over `detail.sessions` only), skip the lookup for the root
    conversation, and test with real numeric ids.
11. **Medium · `worker/memory/chat.ts` ~114 pi's `byOwner`.** The flag follows the last prepared message, plus a
    hand-off count kept in memory, not the turn that is running. Two ways it goes wrong:
    - A hand-off turn resumed after a restart (or after pi's session closes, which rejects `harness.wait`) is no
      longer counted. An owner message sent meanwhile then lets the agent-steered turn save a confirmed "just me" note.
    - A member's running turn saves as the owner after the owner messages and then makes the chat private.

    Fix: decide from pi's running run, durably. For example, a kv record per pi run, written before submit and
    cleared when it settles, or the run's own inputs: owner only when every input is the owner's `chat.message` and
    none is a hand-off.
