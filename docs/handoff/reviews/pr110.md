Four reviewers looked at it (security, delivery, forks, regressions). Each finding was then checked by two more, who

## Must fix

1. **Medium, security · `worker/agents/turns.ts` ~286 `forksFor`.** An owner's turn forks only when its tools include
   an MCP server outside the shared list. App tools (`files_read`, `files_list`, `run_python`, `run_bash`) never count.
   - Example: planner lists only `db`, so everything it uses is shared. The owner asks "@planner read salaries.md and
     total it". The turn runs in the shared session, its live steps go to every socket, and a member's next read-only
     turn can quote the file.
   - It is worse in a seat. The seat's files are the member's own private files (seat.ts ~158), and the room owner's
     next question pulls them out.
   - The spec says shared means "no private files". `agentInstructions` tells the model that every owner turn "runs
     apart from the chat", which is false when it did not fork.
   - Fix: fork whenever the owner's allow-list has a read source that a non-owner turn lacks (any app tool outside
     `READ_TOOLS`, or any MCP tool outside the shared list). Update the `dbOnly` test.
2. **Medium, security · `worker/agents/turns.ts` ~298-313 `resultsIn` / `turnSources`.** The server behind a result is
   looked up in the tool map as it is when the turn ends (`#mcpTools`). A refresh in the meantime can drop a server:
   someone's @pi, an expired sign-in or a restart. A text-only result then counts as an app tool, so a reply built on
   a private calendar posts with no source chip and skips review before posting. Fix: record the server on every MCP
   result at call time (`details.server` in `worker/agent/mcp.ts`, read first). Fail closed: an unknown tool's result
   in a fork counts as private.
3. **Medium, security · `worker/chat-agent.ts` ~2382 a fork's side effects.** What a forked turn publishes or saves
   becomes the chat's at once: `artifact_publish` records the page under the chat, sandbox outputs land in
   `out/<chatId>/`, and `#transcriptTraces` reads fork sessions too. Members see it before the owner reviews, and
   after Discard. A page that calls sign-in servers then also loads for them with the owner's data. Fix: a fork's
   pages and files become the chat's only when its reply is posted, and stay out of the chat's listings until then
   and after a discard. Skip fork sessions in `#transcriptTraces` or keep a set of fork session ids. At the least, with
   review on, hold them.
4. **Medium · `worker/agents/controller.ts` ~177 / `worker/chat-agent.ts` ~3486 live follow of a fork.** `changed()` runs
   before `setSession`, so every socket starts following the shared session, the owner's included, and
   `#followAgents` compares only turn ids. As a result the owner never sees their forked turn live. Fix: call
   `changed()` after `setSession`, and keep a follow only while its turn and session both match.
5. **Medium · `worker/agents/roster.ts` ~353 `askKeys`.** A forked turn's question never reaches the shared session.
   Its key counts as seen, but the input went only into the fork. Later turns get the posted reply but not the ask
   (for example "answer in French from now on"). T4's item 10 added `AND session IS NULL` in #108: check that it now
   covers forks too, and do the same for seats (`batchFor`). Add a test: a forked ask, then a later turn sees it.
6. **Medium · `worker/agents/controller.ts` ~194 failed seat give.** If `seatGive` rejects (a seat reset by a deploy,
   say), the room ends the turn as failed and moves on. The seat's run of that turn keeps going after its restart.
   The next turn then reconfigures the same session in the middle of that run, and the real reply is dropped. Fix:
   retry `give` on transport errors (it is idempotent) before failing. When the room ends a seat turn, abort it at the
   seat. In the seat, abort any other running turn of the same room and agent before configuring the next.
7. **Medium (checkers), security · `worker/agents/turns.ts` ~199 `askLine` in a seat.** Every `pi.user` entry is
   labelled "your owner", whoever's agent reads it, and `chat.message` lines are labelled by uid. A member's agent
   starts its catch-up at -1, so it reads the room owner's old solo messages as its own owner's instructions, on a turn
   with all of the member's tools. Imported entries with crafted uids do the same. Fix: label `pi.user` as owner only
   when the chat's owner is that agent's owner. Start a seat's catch-up where the agent was added (or don't trust uid
   labels from imported entries).

## Should fix

9. `roster.ts` ~379: a forked turn requeued after a restart forks again. Its input may already be placed in the old

12. `src/agents/SetupTab.tsx` ~376: "Review before posting" set while copying a shared agent is dropped (not in
    `COPIED_FIELDS`). Add it or hide the box for copies.
13. `roster.ts` ~278: the alias rule keeps "data-bot" when its owner renames it to "data", though "data" is free. Store

### Must fix

18. **Medium, security · `worker/agent/publish.ts` ~394 `artifactFor`.** Title matching takes over a withheld or
    discarded fork page. The owner discards a planner reply whose fork published "Salaries" (HR data, review on). Later
    pi, in the shared session, publishes a page titled "Salaries": `artifactByTitle(scope.chatArtifacts())` still lists
    the hidden page, so the publish becomes its v2. The id is then in the shared traces, it drops out of `hidden`, and
    members see v1 and can run its HR calls with the owner's sign-in. A member can probe titles on purpose, since the
    forked ask is in the shared session. Fix: leave hidden pages out of title matching unless the publish runs in the
    fork that made them (thread the tool's `api.conversationId` into the scope), and refuse an explicit artifact_id of a
    hidden page from any other session. Test it.
19. **Medium, security · `worker/agents/roster.ts` ~560 / `controller.ts` ~344.** A failed fork, or one done with empty
    text, counts as posted: `#ended` holds only `done && text && review && sources.length`, `#release` sets `posted = 1`,
    and the fork's pages and files show to members without review, with its sign-in calls (a checker's scratch test:
    `failed-fork.test.ts`). Mark a fork posted only when a done reply with text is released or the owner posts it. With
    review on and private sources, keep a failed or empty fork's outputs withheld (post the failure text if you like)
    until the owner posts or discards.
20. **Medium, security · item 3, known gap 1 (and 2).** A fork's new version of a page the chat already has is visible,
    and loadable, before review and after Discard. Members' page calls to a sign-in server it newly declares run with
    the owner's sign-in, because hiding goes by page id. This only lasts past the turn when the agent has review on,
    which is the case review exists for. Fix:
    - Record what a fork publishes at publish time: pass `api.conversationId` to `onPublished`, and when the session is
      an unposted fork, store (session, artifact_id, version). That also closes known gap 2 (an aborted or stopped
      publish has no tool result) and the publish-to-commit window.
    - Gate members' page tools and calls (`artifactTools`, `artifactCall`, which get the version) by id and version
      against those rows.
    - With review on, refuse an unposted fork's publish onto a page the chat already has. The error says to put the
      change in the reply, or to publish a new page, which stays hidden until the reply is posted. Without review a
      fork's outputs are the chat's when its turn ends anyway, so leave that alone.
    - Same for files: with review on, refuse a fork's `files_write` or sandbox output over a file already in the chat.
21. **Medium · `worker/agents/seats/seat.ts` ~162 `#resume`, items 6 and 15.** A second give of a turn (the room's retry,
    or its re-give after a restart) or the new alarm's wake can reach a turn whose first give inserted the row but hasn't
    submitted yet (configure takes seconds). `#await` waits on an operation not submitted, gets `not_found` at once, and
    the seat ends and reports the turn as failed and deletes the row. The first give then submits anyway, nobody waits
    for it, and its reply (and any writes) never reach the room. One checker rated it high. Repro: `seat-races.test.ts`
    tests 1 and 2. Fix: mark a row submitted right after submit (a column, or "starting" then "running"), and keep an
    in-memory set of gives in progress. `#resume` and wake skip a row a give here is still setting up. A known row that
    was never submitted and has no give in progress (its give died with the object) is configured and submitted again
    from the SeatTurn (the operation id places it once). Guard `#await` against a missing row.
22. **Medium · `worker/agents/turns.ts` ~211, a regression from item 1.** Now that every owner turn forks, the agent's
    own session gets only "(your reply, as posted): …", without the pages it published or the files it saved. On the
    owner's next "@planner add a chart to it", the agent can't find the page it just made (there is no list tool), so it
    makes a duplicate. Add the reply's published pages (id, title, version) and saved files to that line; they are the
    chat's once posted. Test it.

28. **Medium, security · `worker/chat-agent.ts` ~1714 `#inChat` (the out/<chatId>/ rule).** A file a fork saves from a
    stopped or interrupted tool counts as the chat's.
    - Scenario: review is on, and the owner asks "@planner total salaries.md into a CSV". Anyone, a member included,
      presses Stop while run_python runs.
    - The harness writes only an aborted tool result, with no `details.saved`. runInSandbox ignores the signal and
      saves `out/<chatId>/totals.csv` (`worker/agent/tools.ts` ~219).
    - The path is in no withheld trace, so the out/ prefix accepts it. contents() lists it to members, and mayOpenFile
      lets them open it, though nothing was posted. A restart during the save loop does the same.

    This is your known gap 2, fixed for pages by recordPage but still open for files. Fix: record what a session apart
    saves at save time, as recordPage does: (session, path) rows written before `files.put` in files_write and
    runInSandbox. `#inChat` then treats paths in unposted rows as hidden, whatever the out/ rule says. Also stop
    runInSandbox from saving outputs once its signal is aborted. Test the Stop case and the restart case.
29. **Medium · `worker/agents/seats/seat.ts` ~442 `abort` / `#restart` / `#start`.** A seat turn the room aborted, or
    one a later give ended, before its input went in is still set up and run.
    - Scenario: Ana's own forked turn ("@planner-ana send the report") is configuring when the seat object dies. The
      room's retries fail, and the controller ends it unanswered and calls seatAbort.
    - That RPC starts the seat, so onStart's wake begins `#restart`. abort() aborts a session that has no run yet, so
      nothing stops. #restart then submits the turn, with Ana's write tools, and its reply is dropped.
    - Ana sees "failed", asks again, and the action happens twice. The review pass's stale-turn fix is defeated the
      same way on a cold seat, and a seatDrop during configure is submitted after the drop.

    A checker reproduced all four. Fix:
    - In abort(), end a running row whose input isn't in yet.
    - In #start, re-read the row just before submit and return unless it is still running. After submit, if the row
      is gone or ended, abort the session.
    - Add the turn to #starting when #restart begins, before its first await.
30. **Medium-low, privacy · drafts are per chat, not per session (your "left open").** This has to be fixed before
    review-before-posting ships. pi's `artifact_drafts` output shows in members' step panels. It lists a fork's
    leftover drafts, including intermediate edits and drafts whose publish was refused, as "for artifact <hidden id>".
    With `draft_id`, it returns the fork's draft HTML. pi can also publish such a draft as a new visible page that calls
    the owner's sign-in servers. Fix: record the session in DraftPage. artifact_drafts, draft_id reads, check and
    publish then leave out another session's drafts while that session is apart and unposted. Test it.
