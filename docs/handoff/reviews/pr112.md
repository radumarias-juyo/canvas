# Lead review of PR #112 (follows and the feed)

Three reviewers looked at it (security, correctness, regressions). Each finding was then checked by two more, who tried
to refute it. The review ran at 57eb4db, and tests and typecheck passed there. Every item below was confirmed by both
checkers unless it is marked "split". Items 1 and 2 were each found twice, independently.

## Must fix

1. **Off the record · `worker/users.ts` ~690 `#touch`, ~814 `recordArtifact`.** A tag item's kind comes from the
   receiver's own sidebar row, and `addFeed` checks that same row as `known`. The chat's real kind is never sent.
   That row is updated off the request path (`#tellKind` → `setChatKind`, only logged on failure), so it can lag.
   - Example: the chat is switched to off the record, and Bea's row write fails or is still queued. "@bea here are the
     numbers" then keeps a tag item, with the excerpt, in her feed, and nothing removes it later.
   - Page versions have the same gap: `recordArtifact` checks only the owner's row.
   - Fix: the chat sends `this.kinds.kind()` with the Tag (and with `onPublished` / `recordArtifact`), and that is used
     as `input.chat.kind`, with the row kept as the extra `known` check. Also drop a chat's items in `setChatKind` when
     it becomes off_record. Add a test with a stale row.
2. **`worker/chat-agent.ts` ~3183 `#deliverRun` and `worker/users.ts` ~693.** A run that notifies its owner adds two
   items for one report: a `tag` ("… mentioned you") from `#touchIndexes`, and a `run` ("sent its report") from
   `onEnded`. A delivery placed again after a restart adds another tag, because the tag ref uses `Date.now()`. Fix:
   keep a run's own post out of the tag path (a flag on the Tag when the reply carries `run`), and make tag refs come
   from the post's request id so a re-placed post maps to the same item.
3. **(split, my call) `worker/feed/store.ts` ~96-105, Needs you.** One checker read this as the documented design, the
   other as a defect. I side with the second.
   - The list filters on `needs = 1` (Unread off by default), but the count only counts `read = 0`, and nothing ever
     clears `needs` except a run's replaced ref.
   - So a confirmed assumption stays listed with "To confirm".
   - A question the person only opened drops out of the count without being answered: seeing a chat reads its items.
   - Fix: keep "needs you" as its own resolved state. Clear `needs` when the thing is answered: the assumption confirmed
     or the agent turned on, a question answered by the asker's next message in that chat, an approval decided (T6).
     Don't clear it on a mere read. Then both the list and its count use `needs = 1`.

## Should fix

4. `worker/users.ts` ~986: an assumption item is resolved only by turning the agent on. Confirming every Assumed field
   in Setup and saving (origin "user", `assumed` gone) leaves it. Resolve `assumptionRef(id)` in `saveAgent` when a
   user save leaves no assumed fields.
5. `worker/feed/store.ts` ~336: followers who left the chat they followed an agent from are never forgotten. `fanOut`
   forgets only when a delivery returns false, and `stillIn` just skips them. In a page chat (anyone may join) they
   fill MAX_FOLLOWERS (500) and block new follows. Forget uids that `stillIn` leaves out because they left. In
   `removeSharedChat`, drop follows made through that chat.
6. `worker/feed-routes.ts` ~47: `POST /api/follows` writes the owner's side first. A fan-out between the two writes
   finds no follow on the follower's side, so the owner forgets them, and they stay half-followed for good. Write the
   follower's side first, then the owner's, and roll the first back if the owner refuses.
7. `worker/feed/store.ts` ~172: follows and `about` are keyed by target id without the owner. Agent ids are unique only
   per user, and an import keeps the id. So unfollowing Ann's agent X deletes the follower's own run items for their
   own X, and following a second owner's X overwrites the first. Key follows by (kind, target_id, owner_uid), and write
   `about` with the owner for followed targets.
8. `worker/chat-agent.ts` ~2694 `#feedQuestion`: a question asked by the owner's second seat is written to a directory
   for the seat's uid, which has no account. Use `this.#account(asker)`, as the other per-person calls do.
9. Data export: follows are the user's own choices and should go with the export and import (`worker/data-routes.ts`,
   `shared/data-export.ts`), with the owner side rebuilt on import. Feed items can stay out. Say that in the README's
   export section.

### Should fix
