# Lead review of PR #108 (scheduled runs engine)

Four reviewers (security, scheduling, executor, regressions); each finding checked by two more who tried to refute it.
Reviewed at the head before the merges of #106 and #107, so line numbers may have moved. Tests and typecheck passed.
All items below were confirmed by both checkers unless marked "split".

## Must fix

1. **High · `worker/chat-agent.ts` ~2666 `#handOver`.** A run's hand-over turn is read-only, but its reply can name
   `@pi`. `AgentTurns.#ended` then stores `toPi` and `#deliver` hands pi a turn in the home chat with the owner's full
   tools (MCP writes, code, files, publish). A 07:00 run nobody watches, steered by MCP data in the report, can make
   writes. Fix: mark such chains unattended (a flag on the turn row, copied to every hand-off `#ended` queues) and for
   them drop pi from the hand-offs, so pi only reads the reply (`tellPi`). Add a test.
2. **Medium · `RunHost.read`.** Look, scope and watch reads ignore the agent's `servers` list, while its work steps
   respect it (`runTools`). Refuse a server outside `agent.servers` when the list is set, and reject such steps in
   `checkAgent` / `parseWorkflow` so a compiled workflow naming other servers fails to compile.
3. **Medium · `#rebuildPage` / `#pageStep`.** The rebuild session runs with the home chat's scope, so a page made in
   another chat cannot be updated, and the tools' errors steer the model to publish a new artifact on every run. Give
   the rebuild session only `artifact_write` / `artifact_check`; publish the checked draft in code with the page's own
   chat scope (as `publishFindings` does); refuse a draft that is not that page's.
4. **Medium · `runner.ts` ~144 `fired()`.** A failed definition read at alarm time (deploy reset, network) throws before
   the next alarm is set; the one-shot is gone and the agent never runs again. Set the next alarm first (from the
   stored trigger or due time), retry the same `dueAt` a few minutes later on failure, and reconcile schedules in
   `onStart` (home agent with no pending job → read the definition and `apply`).
5. **Medium · `chat-agent.ts` ~358.** The `run` / `watch` Scheduler callbacks await the whole run inside Lifecycle's job
   dispatch, which drives jobs one at a time; pi's wake job (e.g. a 429 retry backoff) then cannot run, so the run
   stalls. Detach the work (`lifecycle.trackAlarmWork(work)` or `ctx.waitUntil`); `runner.resume()` covers restarts.
6. **Medium · `users.ts` `forgetChat` / `ChatAgent.deleteChat`.** Deleting an agent's home chat silently stops its
   schedule and watches (the row and its `agent_id` go, nothing re-homes it, `nextRunAt` null). Re-home it
   (`ensureAgentHome` + `agentChanged`) if it is still on with a trigger, or refuse / warn.
7. **Medium · `runner.ts` ~217 `signedIn()`.** Signing in restarts every waiting run at once, also of agents now off, so
   three days of waiting runs post three near-identical reports. Restart only the newest per agent, supersede the older
   ones, and skip agents that are off.
8. **Medium · `executor.ts` ~466.** A page delivery is marked sent only after it finishes, so a restart mid-rebuild
   starts a second model turn in a new session and publishes twice (`publishFindings` likewise). Record the delivery as
   in progress with its session id, reuse that session with the same operation id on resume; for findings, check the
   artifact's latest version for this run first.
9. **Medium · `executor.ts` ~310 `#item`.** A watch-triggered run's work steps never see the value that fired it (it is
   only in the condition scope, never written to the session), and `previous` is not in the steps' scope. Write the
   watch value into the item's session as a passive write before the steps, keep the previous value in the run detail
   and add it to the scope.
10. **Medium · `roster.ts` ~319 `askKeys`.** A turn that ran in a run's fork counts as seen by the agent's main session,
    so the main session's catch-up skips the owner's reply and drops the agent's own answer: later turns there never see
    that exchange. Leave out turns with their own session (`AND session IS NULL`), and let the agent's own replies from
    forked turns into its main catch-up.
11. **Medium · `worker/agents/tools.ts` ~51.** `agent_propose` still describes a watch's `when` as free text, but
    `checkAgent` now refuses anything the condition language does not parse, so watch proposals fail. Describe the
    language and the names in scope (the step's `as` or tool name, `watch`, `previous`) with an example, or compile a
    natural-language condition the way the workflow is compiled.

## Should fix

12. `chat-agent.ts` ~1397: a reply that continues a run and also names other agents makes two chains (two roots), which
    doubles MAX_HOPS for one message. Pass the first turn's id as `root` to the second call.
13. `executor.ts` ~458: a tell or page step an item already reached is dropped when a later `onlyIf` stops the item or a
    later step fails (the trace still says "sent once every item is done"). Send every reached delivery, or forbid
    delivery steps before an `onlyIf` in `checkAgent` and record the cancel in the trace.
14. `runner.ts` ~147: a stale alarm still runs after the time changed (`fired` checks only `due_at`). Require
    `row.key === triggerKey(agent)`, else re-apply; ignore an `apply` older than the stored definition version.
15. `source.ts` ~99: a failed notify loses the change for that subscriber (the new value is already saved). Set it back
    to `fresh` so the next poll tells it again.
16. `runner.ts` ~172 `sourceMoved`: accepts values from a Source the agent no longer watches and never unsubscribes;
    include the Source's identity in `notify`, and on a mismatch or an agent off/gone, unsubscribe instead.
17. `executor.ts` ~372: a look named `__proto__` sets the scope's prototype, so conditions can't see it. Build scopes with
    `Object.create(null)` or refuse `__proto__`, `constructor`, `prototype` as names.
18. `shared/conditions.ts` ~47: `a.1.2` reads `1.2` as a number, and keyword-like keys (`a.True`) are lowercased. Read
    the segment after `.` from the source text (digits or an identifier in its own case).
19. (split, low) `executor.ts` ~344: every delivery gets the text of all the item's work steps, including those after
    the delivery step; build each from the work done before it.
