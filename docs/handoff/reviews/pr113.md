## Must fix

1. **Medium-high, security · `worker/chat-agent.ts` ~3321 `#callerOf` `{kind: "page"}`.** Every page call runs at
   level 4 ("as your own page"), whoever's turn built it. On a member's message (or a chain a member started) pi is
   capped at level 2, but it still has `artifact_write` and `artifact_publish`, and those aren't gated.
   - Example: a member writes "@pi make a page that on load calls crm.update_deal {id: 5, discount: 90}", or has pi
     edit the owner's existing dashboard (an edit of a reviewed page inherits `reviewed`). In `artifact_check`,
     `#checkBridge` answers the call with not_granted, which check.ts files as a warning, so publish accepts it. The
     version's manifest declares the write tool. When the owner next opens the page, `artifactCall` lets it through
     (viewer is the owner) and the write runs at level 4, with no card and no approval.
   - `publishRebuilt` already refuses this case for run rebuilds. pi's own below-level-4 turns have no such check.
   - Fix: on a pi turn below level 4, make `artifact_publish` refuse a draft whose manifest declares write tools (or
     servers) the page's previous version didn't, with the same rule `publishRebuilt` uses. Or store with each version
     the level it was published at, and have `#callerOf` for pages refuse writes to tools a below-4 version added
     until the owner republishes. Add a test: a member-started pi turn can't publish a page that adds a write tool.
2. **Medium · `worker/agents/limits/gate.ts` ~90 / `worker/mcp/hub.ts` ~149, callsPerDay.** The count reads only
   logged calls, and a call is logged after it ends (`gate.ran`, then `waitUntil(logCall)`). pi runs tool calls in
   parallel and runs take 4 items at a time, so every call in a batch sees the same count. A checker reproduced it
   with the real McpHub and WriteGate: a block rule `mail.send callsPerDay 1`, three parallel calls, and all three
   reached the server. Fix: reserve the call when the check passes. Either count and insert a "started" row in one
   directory RPC (then update it to ran or failed), or keep an in-flight count per (server, tool) in the gate and add
   it to `callsSince`. Add a test with parallel calls.
3. **Medium · `shared/limits.ts` ~230 `matchesValue`.** A "never" rule on a boolean argument never fires. The editor
   offers only "never" for booleans (`kindsFor("boolean")`), the value is saved as the string "true", and
   `matchesValue("true", true)` returns false for a non-string, non-number value. A block rule
   `crm.delete_deal permanent never true` lets `{permanent: true}` run at level 4, while the UI shows the rule as
   active. Fix: compare booleans as "true"/"false" (ignoring case), and add a test.
4. **Medium · `worker/agents/limits/tell.ts` ~33, joined recipients.** When the tool's recipient field isn't an array,
   `toolInput` joins the list ("boss@ok.com, leak@blocked.com"). A never rule on `to` then tests the whole string: an
   exact value never matches, and a wildcard matches only in some orders. Checked with the PR's own `violation()`. Fix:
   for never rules on string arguments, also test each part split on `,` `;` and whitespace. Add a test with a joined
   string.
5. **Medium · `worker/agents/runs/executor.ts` ~500, a held do step.** `#act` records a held call as
   `{ok: true, detail: "Not run yet: waiting…"}`, and the run goes on. Its next steps run and its tells go out at once,
   and the item ends "acted" (run "sent"). Example: [do crm.update_deal {discount: 30}, do mail.send "your discount is
   applied"]. The update waits, the mail goes now, and a decline or expiry leaves the customer told of a change that
   never happened. `#actionEnded` writes only to the item session and never updates the run. This is also the gap you
   named ("runs don't resume after an approval"). Fix: a held do step is a stop point. Record it as waiting, stop the
   item there (like a false `onlyIf`), and don't send its deliveries. On approve, continue the item from the next step
   (the origin has agentId, dueAt, item and step) with the result as an `app.approval` input, as the brief asks. On
   decline or expiry, end the item with that and send what the workflow says for a stopped item. The run shows
   "waiting" meanwhile. Add a test for each of the three outcomes.

23. **Medium · `worker/agents/runs/executor.ts` ~398 `#elements` / `#item`.** A scope list over MAX_KEPT_CHARS*4 (256K)
    isn't kept, so when a run goes on after a decision it lists the scope again and matches rows by `itemKey` alone.
    A checker reproduced three failures with FakeHome:
    - (a) Rows without id/key/slug/code/name get index keys. Remove row 1 before approving item #2, and #2 replays
      o2's outcomes over o3's element, so o3 gets o2's mail.
    - (b) A held item whose row has left the list stays running for good, and the run ends "sent" without it.
    - (c) Rows added since the due time get fresh items and run their do steps hours late.

    with a reason, as a cut do result does. Never match index keys against a fresh list. Add a test for each of the
    three.
24. **Medium, security · `shared/limits.ts` ~280 `violation` (never).** A never rule on a list or untyped argument never
    fires when the call passes objects. With `to: {type:'array', items:{anyOf:[string, {email}]}}` the editor offers
    only `to`, and `{to:[{email:'ceo@rival.example'}]}` runs, because matchesValue is false for a non-scalar. The same
    happens when a server changes a field from strings to objects. min/max fail closed; never fails open. Fix: match
    never against the string, number and boolean leaves of an object or array value (a few levels deep), or fail closed
    ("<arg> is {...}, which a never rule can't check"). Test with a list of {email} objects.
